# Changelog

## 0.5.0 — The template is built during construction

The runtime API grew; the *contract* changed in a way that affects
every host class.

0.4.x built the template **lazily**, on the first read of a generated
field. Nothing forced that read, so a window came up **empty** — the
widget existed, the template was never instantiated. GTK builds a
widget's template in the instance initializer; Dart has no instance
initializer (a field initializer cannot touch `this`), so the host
widget now builds its template itself:

```diff
 class TodoWindow extends AdwApplicationWindow with _$TodoWindowTemplate {
-  TodoWindow(super.app);
+  TodoWindow(super.app) {
+    initTemplate();
+  }
 }
```

`initTemplate()` is the generated mixin's override of
`GtkWidget.initTemplate()`. It is idempotent.

### New helpers

- `widgetTypeOf(GtkWidget)` — the instance's native `GType`. A Dart
  subclass has no `GType` of its own, so this is the type GTK sees.
- `prepareTemplateXml(String, int)` — prepares the user's XML for
  GTK: it rewrites the `<template>` element's `class` and `parent`
  attributes to the instance's real native type and that type's
  parent (GTK checks both and rejects a mismatch), and it removes the
  `<signal>` elements (GtkBuilder would resolve the handler as a C
  symbol, which a Dart class cannot provide).
- `rewriteTemplateTypes(String, String, [String?])` and
  `stripTemplateSignals(String)` — the two pure halves of the above.
- `claimTemplateType(int, String)` — GTK allows one template per
  native class and a Dart subclass does not register a `GType` of its
  own, so two Dart template classes cannot share one native widget
  type. The second one is rejected with a `StateError` instead of
  tripping a GTK assertion.

### Other changes

- `getWidgetClass` is unchanged; it now shares its type lookup with
  `widgetTypeOf`.
- The generated code no longer needs `package:gobject/gobject.dart`:
  the children are resolved against the *widget's* native type — the
  type that declared them — not against the child's type.

## 0.4.0 — Part-file contract

The runtime API is unchanged. The *builder's* output contract
changed, and this package's documentation follows it.

The generated mixin is now a `part of` the user's library, and
there is **one part file per source file** rather than one per
class. The part file's name is derived from the source file's
name alone — `my_window.dart` → `my_window.g.dart` — the same
convention `json_serializable` uses.

```diff
-part 'my_window.mywindow.g.dart';
+part 'my_window.g.dart';
```

Because the mixin lives in the user's library, the trampoline
resolves the user's instance method names at compile time. The
dispatch goes through `dynamic`:

```diff
-button.onClicked(() => this.onClicked());
+button.onClicked(() => (this as dynamic).onClicked());
```

The mixin is declared `on <ParentType>`, and the analyzer
rejects a call to a member the parent type does not declare —
the user's method is declared on *their* class, not on the
parent. `dynamic` defers the call to the runtime class's
method table without giving up static analysis on the rest of
the mixin.

A `part of` file inherits its library's imports and cannot
declare its own, so the library must import
`package:gtk4/gtk4.dart`, `package:gobject/gobject.dart` and
the package that declares the parent widget type. The builder
checks this and fails with the exact import lines to add.

See the [builder's changelog](../gtk_templates_builder/CHANGELOG.md)
for the full list of changes.

## 0.3.1 — Callback trampoline

The builder now auto-wires `<signal name="X" handler="Y"/>`
entries from the template XML to user-declared instance
methods, so the user no longer has to call
`connectSignal(...)` from their constructor. The
codegen-emitted `_$<className>Template` mixin calls
`child.on<SignalName>(() => this.<Y>())` per signal
during `_ensureInstanceInit`, after the children are
populated by `getTemplateChild`.

The user's instance method name must match the XML's
`handler="..."` attribute, converted from snake_case
to `lowerCamelCase` (`on_clicked` → `onClicked`). The
arity must match the GIR-declared arity of the FFI
binding's `on<SignalName>(...)` overload — e.g.
`clicked` on `GtkButton` is `void Function()`, so the
user method takes no arguments. Mismatched arity
surfaces as a runtime type error when the signal fires,
not a build-time diagnostic.

The runtime re-exports `GBytes` from `package:glib` (the
record generated by `gir_generator` from the glib
`<glib:boxed>` declaration) so user code needs a single
import. `gbytesFromString` and `gbytesFromUint8List`
remain as thin FFI wrappers over `g_bytes_new`, looked
up via `package:glib`'s `glibLookup`.

## 0.3.0 — Codegen runtime support

- New `GBytes` record and `gbytesFromString(String)` helper
  in `package:gtk_templates`. `GBytes` is the record
  generated by the `gir_generator` for the glib `<glib:boxed>`
  declaration; the `gbytesFromString` helper is a thin FFI
  wrapper over `g_bytes_new` (looked up via `package:glib`'s
  `glibLookup`). The codegen-emitted mixin uses
  `gbytesFromString` to wrap the embedded template XML
  before passing it to `GtkWidgetClass.setTemplate(...)`.
- The generator now parses `<glib:boxed>` from the glib
  namespace's GIR, so `GBytes` (and the other glib boxed
  types) flow through the standard emit path. The
  `gtk_templates` package re-exports the generated `GBytes`
  so user code has a single import.

## 0.2.0 — Breaking change

`@GtkTemplate`'s single mandatory keyword argument is now `source:`,
of type `GtkTemplateSource`. The two variants are:

- `GtkTemplateXml(content)` — the raw XML string, embedded as a
  Dart string literal at the call site.
- `GtkTemplateFile(path)` — a path to a `.ui` file, resolved
  relative to the **package root** (the directory holding
  `pubspec.yaml`).

The 0.1.0 form `@GtkTemplate(resourcePath: '/com/myapp/window.ui')`
is **gone**. `GtkWidgetClass.setTemplateFromResource` is no
longer in the codegen dispatch; users who need it call the
lower-level API directly outside the `gtk_templates` system.

### Migrating from 0.1.x

```dart
// 0.1.0 — gone.
@GtkTemplate(resourcePath: '/com/myapp/window.ui')
class A extends GtkBox { ... }

// 0.2.0 — file in the package source tree.
@GtkTemplate(source: GtkTemplateFile('lib/myapp/window.ui'))
class A extends GtkBox { ... }

// 0.2.0 — inline XML, for short templates and tests.
@GtkTemplate(source: GtkTemplateXml('''
<interface>
  <template class="A" parent="GtkBox"/>
</interface>
'''))
class A extends GtkBox { ... }
```

For users with a `.ui` file at a known package-root-relative
path, the `file:` form is the direct replacement. The codegen
reads the file at build time and embeds its contents as a
string; the runtime path is then identical to the `xml:` form.

## 0.1.0

Initial release.

- `@GtkTemplate`, `@GtkTemplateChild`, `@GtkTemplateCallback`
  marker annotations read by `package:gtk_templates_builder`.
- `getWidgetClass(GtkWidget)` runtime helper used by the
  codegen-emitted `_$ClassTemplate` mixin to walk from a widget
  instance to its `GtkWidgetClass*`.
- `snakeCase(String)` conversion used by the mixin when
  registering callback symbols. Mirrors PyGObject's
  `camel_to_snake` (no coalescing of trailing capitals — GTK
  template symbols don't tend to have them).
